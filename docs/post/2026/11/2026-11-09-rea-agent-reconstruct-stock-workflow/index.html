REA는 에이전트의 도구 상자다

영상은 REA를 “AI에게 프로그램을 살펴볼 도구 상자를 연결하는 것”으로 비유한다. 분석 대상과 기능을 정하면 에이전트가 REA를 통해 화면과 동작을 관찰하고, 그 근거를 사용해 코드를 작성한 다음 원본과 비교한다. 공식 사이트도 REA를 웹사이트·JavaScript/Electron 앱·네이티브 바이너리 등의 동작을 코딩 에이전트가 조사하도록 연결하는 도구로 소개한다. 영상 00:20, REA 공식 사이트

원본 주식 분석 사이트에서 읽어낸 구조

영상의 원본은 종목을 가져와 차트와 수급 조건으로 후보를 좁히는 노드형 분석 화면이다. 각 블록은 역할을, 연결선은 결과가 다음 단계로 넘어가는 경로를 나타낸다. 블록을 선택하면 설정과 결과를 확인할 수 있고, 투자 방식의 조건을 통과한 종목, 투자 비중과 위험 점검 단계도 흐름 안에서 추적한다. 영상 00:43, 영상 01:03

미국 종목 흐름에서는 종목 선택 뒤 SEC 공시 자료와 언어 모델 분석, 차트 표시가 이어진다. 실행 중에는 어느 단계까지 진행됐는지가 블록에 표시되고, 자료를 모으는 단계와 해석하는 단계를 분리해 볼 수 있다. 영상 속 실행은 답변 길이 제한으로 최종 답변이 나오지 않았으며, 오류 이후 어디를 보완할지 확인하는 장면도 포함한다. 이는 파이프라인이 화면에 보인다고 해서 분석이 완료된 것은 아님을 보여준다. 영상 01:31, 영상 01:54

설치는 도구 연결과 실행 환경 정리다

영상에서는 REA 공식 GitHub의 설치 문서를 Claude에 전달하고, 필요한 도구와 현재 설정을 확인하게 한다. 제작 환경의 Node 버전을 맞추고 REA가 연결되는 실행 환경을 정리한 뒤, 네이티브 프로그램 분석에 쓰는 Ghidra도 추가 설치한다. 영상은 Ghidra가 웹사이트를 볼 때 항상 필요한 것은 아니며, 도구가 설치되고 연결되는 과정을 확인하는 용도라고 설명한다. 영상 02:14, 영상 02:57

REA 공식 저장소는 JavaScript/Electron, 웹사이트, 네이티브 바이너리 등 분석 대상에 따라 필요한 공급자가 다르다고 설명한다. Ghidra는 NSA Research Directorate가 만든 소프트웨어 역공학 프레임워크로 디스어셈블·디컴파일·그래프·스크립팅을 제공하지만, 웹 브라우저 관찰에 Ghidra가 자동으로 필요한 것은 아니다. 대상별 도구와 권한을 최소화해 설치하는 편이 안전하다. REA GitHub, Ghidra 공식 설명

새 구현은 “전체 복사”가 아니라 수직 슬라이스다

원본 사이트를 REA로 관찰한 뒤 제작자는 모든 기능을 한 번에 넣지 않고, 노드 편집기와 핵심 노드부터 구현하기로 선택한다. 시세를 어디서 받을지, 어떤 개발 방식을 쓸지 정하고, 이 시연에서는 Binance와 Python FastAPI, 단일 HTML 구성을 선택한다. 이 선택은 원본의 서버 코드를 가져온 것이 아니라, 관찰한 입력·출력과 화면 구조를 새 기술 조합으로 다시 만든 것이다. 영상 04:11, 영상 04:28

구현 순서도 수직 슬라이스에 가깝다. 먼저 시세를 가져와 보관하는 부분을 만들고, 노드별 입력과 출력의 계산 규칙을 작성한 뒤, 실행 서버와 API를 연결한다. 실제 데이터로 한 번 흐름을 돌린 다음 노드 편집기 화면을 만든다. 영상에서는 아홉 개 노드 실행이 성공한 결과가 표시된다. 영상 04:47, 영상 05:09

REA는 관찰과 검증에 두 번 쓰인다

영상의 마지막 정리는 REA가 두 군데에서 사용됐다는 것이다. 첫째, 원본 사이트를 열어 화면·구조·오가는 데이터를 기록한다. 이 과정에서 17가지 노드 정보도 얻었다고 설명한다. 둘째, 새 사이트에서 템플릿을 고르고 실행한 뒤 화면이 열리는지 직접 클릭해 검사한다. 중간 분석 자료는 저장하고, 큰 페이지 코드는 내려받아 일반 도구로 검색한 뒤 Claude가 구현에 사용한다. 영상 07:09, 영상 07:40

실전 적용 포인트

  1. 관찰 질문을 기능 단위로 쪼갠다. “사이트를 복제해 줘” 대신 노드 생성, 연결, 실행, 결과 표시처럼 확인할 행동을 목록으로 만든다. 영상 00:20
  2. 원본과 새 구현의 경계를 적는다. 화면·입력·출력만 재현하는지, 서버 계산과 데이터 소스까지 대체하는지 명세에 분리한다. 영상 03:58
  3. 최소 수직 슬라이스를 먼저 만든다. 시세 수집 → 노드 계산 → API 실행 → 화면 표시가 한 번 끝까지 흐른 뒤 기능을 확장한다. 영상 04:11
  4. 관찰과 검증에 같은 체크리스트를 쓴다. 원본에서 확인한 템플릿, 입력, 상태, 결과를 복제본에서도 클릭·실행해 본다. 영상 07:09
  5. 금융 결과는 연구용으로 격리한다. 데이터 최신성, 결측치, 계산 규칙, 거래 비용과 리스크 한도를 검증하기 전에는 매매 자동화나 투자 추천으로 확장하지 않는다. 영상 01:17
  6. 권한과 허가를 먼저 확인한다. REA와 분석 대상은 본인이 소유하거나 분석 권한을 받은 것에만 사용하고, 인증·보호 장치·비공개 서버를 우회하지 않는다. REA GitHub

핵심 요약

  • REA의 가치는 복제 버튼이 아니라 코딩 에이전트가 관찰·분석·검증 도구를 호출하게 만드는 데 있다.
  • 영상의 주식 사이트 사례는 원본의 화면과 관찰된 입출력을 새 노드형 UI와 데이터 파이프라인으로 재구성한 첫 버전이다. 영상 05:35
  • REA는 원본을 볼 때와 복제본을 검사할 때 모두 사용되며, 두 결과를 비교해야 수정 루프가 만들어진다. 영상 07:40
  • 비슷한 UI는 서버 계산의 동일성이나 투자 판단의 유효성을 증명하지 않는다. 금융 분석 결과는 연구용으로 검증해야 한다. 영상 07:57

결론

REA와 Claude를 결합한 흐름은 완성된 소프트웨어를 무작정 복사하는 기술이라기보다, 관찰 가능한 동작을 근거로 독립 구현을 빠르게 만드는 개발 방법에 가깝다. 가장 좋은 사용법은 작은 기능 하나를 선택하고, 원본 관찰 기록과 새 코드의 검증 결과를 남기는 것이다. 특히 주식 분석처럼 결과의 책임이 큰 영역에서는 화면의 유사성보다 데이터 계약, 계산 규칙, 오류 처리, 리스크 검증을 먼저 완성해야 한다.
