Claude Code 최신 베스트 프랙티스: CLAUDE.md를 줄이고 검증·훅·오케스트레이션을 강화하는 법

Claude Code가 코드를 잘 작성하지 못하던 시절의 설정을 그대로 유지하면, 모델이 좋아진 뒤 오히려 작업을 방해할 수 있습니다. Anthropic Claude Code 팀의 Lydia Hallie가 소개한 최신 베스트 프랙티스는 지시문을 줄이고, 위험은 권한·샌드박스에 맡기며, 결과 검증은 테스트와 훅으로 자동화하고, 여러 세션은 별도 지휘 세션이 관리하는 방향으로 바뀌었다고 설명합니다.

1. CLAUDE.md는 “모델이 볼 수 없는 사실”만 남긴다

예전에는 중요한 규칙마다 IMPORTANT, NEVER, 느낌표를 붙여 강하게 강조하는 방식이 권장됐지만, 영상은 최신 모델에 이런 과도한 강제가 오히려 불필요한 작업이나 잘못된 방향을 유발할 수 있다고 설명합니다. 코드에 이미 드러난 기술 스택·파일 위치·일반적인 실행 방법은 CLAUDE.md에서 지워도 됩니다. 영상 1:04

남겨야 하는 것은 저장소만 읽어서는 알기 어려운 사실입니다. 예를 들어 오래된 서비스가 더 이상 사용되지 않는 것처럼 보이는 모듈을 실제로는 런타임에 가져가거나, 특정 배포 순서·조직 정책·금지된 외부 시스템이 있는 경우입니다. 이는 “문서 최소화”가 아니라 중복 지시를 제거하고 숨은 제약을 보존하는 작업입니다.

영상은 /doctor prompt-audit 같은 프롬프트 감사 명령으로 현재 모델과 스킬을 기준으로 불필요한 지시를 찾아낼 수 있다고 소개합니다. 영상 1:46 실제 명령과 제공 여부는 Claude Code 버전에 따라 다를 수 있으므로, 실행 전 현재 도움말을 확인하세요.

2. 자동 모드의 경계는 거부 규칙과 샌드박스로 나눈다

영상은 자동 모드가 승인 요청을 사람보다 더 잘 막는 실험 결과를 소개하지만, 위험한 명령 일부는 여전히 통과할 수 있다고 강조합니다. 자동 모드는 “안전 보장”이 아니라 승인 피로를 줄이는 도구입니다. 영상 1:57

거부 규칙: 명령이 실행되기 전에 차단

API 키와 비밀번호가 있는 .env 파일이나 비밀 디렉터리처럼 절대로 읽으면 안 되는 대상은 거부 규칙에 명시해야 합니다. 직접 파일을 읽는 명령이 규칙과 일치하면 모델이 파일을 열기 전에 차단할 수 있습니다. 영상은 기본 자동 모드에서 .env를 읽으면 키가 대화 기록에 남을 수 있다고 경고합니다. 영상 2:26

샌드박스: 승인된 명령 내부의 부작용까지 제한

거부 규칙만으로는 충분하지 않습니다. 예를 들어 npm test 자체는 허용된 명령이지만, 테스트 중 실행되는 서드파티 패키지가 .env를 읽어 외부 서버로 전송할 수 있습니다. 샌드박스는 파일시스템과 네트워크 경계를 운영체제 수준에서 적용해 이런 간접 접근을 줄입니다. 영상 2:51 Anthropic도 샌드박스를 파일시스템·네트워크 제어를 제공하는 안전 계층으로 설명합니다.

거부 규칙은 직접 실행되는 명령에, 샌드박스는 그 명령과 종속성이 닿을 수 있는 자원에 적용된다고 이해하면 됩니다. 장시간 작업을 클라우드 세션에서 실행하면 로컬 .env와 키가 자동으로 따라가지 않지만, 클라우드에 코드를 올리거나 메시지를 보내는 작업도 되돌릴 수 없을 수 있으므로 동일한 거부 규칙을 유지해야 합니다. 영상 3:25

3. “끝났다”가 아니라 테스트가 의도한 동작을 증명해야 한다

영상은 같은 로그인 API 교체 작업을 시켜도 어떤 실행에서는 이전 API가 남고, 다른 실행에서는 모든 사용자가 로그아웃되는 예를 듭니다. 코드가 정상적으로 끝난 것처럼 보여도 결과가 요구사항과 다를 수 있다는 뜻입니다. 영상 3:51

따라서 테스트는 단순히 예외가 없는지 확인하는 데 그치지 말고, 잘못된 구현을 구분할 수 있는 시나리오를 실행해야 합니다. 로그인 마이그레이션이라면 기존 세션이 유지되는지, 새 세션은 새 API를 사용하는지, 토큰 만료가 예상대로 처리되는지를 직접 검증해야 합니다.

Anthropic의 강연 요약도 테스트가 에이전트가 의도한 결과를 만들었는지 판별해야 하며, 단순한 타입 검사만으로는 부족하다는 방향을 제시합니다. 작업 중간 테스트를 돌리면 사람은 수 시간의 diff 대신 실패한 검증부터 확인할 수 있습니다. 영상 4:12

4. 훅은 검증을 “항상 실행되는 규칙”으로 만든다

Claude Code의 훅은 특정 이벤트가 발생할 때 미리 정한 명령을 실행합니다. 파일 수정 후 포맷·정적 분석을 실행하거나, 작업 완료 전에 테스트를 실행하도록 설정할 수 있습니다. 영상은 에이전트가 테스트를 매번 실행한다는 보장이 없으므로 훅으로 강제해야 한다고 설명합니다. 영상 4:32

특히 종료 코드가 중요합니다. 영상 설명에 따르면 훅이 1로 끝나면 오류가 있어도 작업을 막지 못하지만, 2를 반환하면 실패 내용이 Claude Code에 전달되어 수정 루프를 시작할 수 있습니다. 영상 4:54

5. 여러 세션은 CI와 독립 리뷰어로 검증한다

수십 개 세션이 동시에 코드를 변경하면 각각의 작업이 끝났다는 사실만으로는 충분하지 않습니다. 영상은 모든 세션의 결과를 합치기 전에 동일한 CI 검사를 통과시키고, 작성한 세션과 다른 Claude 세션이 코드를 검토하도록 하는 Anthropic 내부 흐름을 설명합니다. 문서·문구처럼 위험이 낮은 변경은 자동 검사만으로 병합하고, 일반 기능은 한 명, 위험한 변경은 두 명이 검토하는 식으로 위험도에 따라 사람의 개입을 조절합니다. 영상 5:17

6. Fable 지휘 세션과 Opus 작업 세션

영상 후반부는 아직 베타 단계인 다중 세션 오케스트레이션을 소개합니다. 사용자는 지휘 세션에 이번 주 작업을 한 번에 전달하고, 지휘 세션이 일을 작은 단위로 나누어 작업용 세션을 생성합니다. 지휘 세션은 팀장처럼 분배·검토하고, 작업 세션은 실제 코드를 작성하는 실무자처럼 동작합니다. 영상 6:11

영상의 예시는 지휘 세션에 Fable 5.2, 코드 작성 세션에 Opus 5.5를 선택합니다. 작업 세션이 결과를 보고하면 지휘 세션이 테스트 통과 여부를 확인하고, 문제가 남아 있으면 다시 수정하도록 지시합니다. 작업 기록이 길어지면 자동으로 정리해 사람이 세션마다 개입하지 않도록 합니다. 영상 6:35

단계별 도입 순서

처음부터 수십 개의 클라우드 세션을 띄우기보다 다음 순서로 안전성을 확인하는 편이 좋습니다.

  1. CLAUDE.md에서 코드에 이미 있는 설명과 숨은 제약을 분리합니다.
  2. 자동 모드 전에 .env, 키, 배포 명령에 대한 거부 규칙을 작성합니다.
  3. 샌드박스에서 파일시스템·네트워크 경계를 설정합니다.
  4. 핵심 사용자 시나리오를 검증하는 테스트를 작성합니다.
  5. 파일 수정·작업 종료 훅을 연결하고 실패 시 exit 2를 반환하게 합니다.
  6. CI에서 모든 세션의 변경을 동일하게 검사합니다.
  7. 작은 작업 두 개로 지휘 세션과 작업 세션의 분배·재시도 흐름을 시험합니다.
  8. 마지막에만 장시간·다중 세션 작업으로 확장합니다.

영상은 평소보다 훨씬 큰 작업을 맡겨 어디서 멈추고 언제 사람의 도움이 필요한지 관찰하라고 권합니다. 시작 전에 자동 검사가 실제로 작동하는지, 필요한 키와 접근 대상이 작업 환경에 준비됐는지를 확인해야 합니다. 영상 7:50

핵심 요약

  • 컨텍스트 최소화: CLAUDE.md에는 코드에서 추론할 수 없는 숨은 제약만 남깁니다.
  • 권한 분리: 거부 규칙은 직접 명령을 실행하기 전에 막고, 샌드박스는 허용된 명령과 종속성이 접근할 수 있는 영역을 제한합니다.
  • 검증 자동화: 테스트는 그럴듯하지만 틀린 결과를 구분해야 하며, 훅은 검증이 매번 실행되게 합니다.
  • exit 2 루프: 훅 실패를 Claude에 전달해 수정→재검증 루프를 만들 수 있습니다.
  • 다중 세션: CI와 독립 리뷰어로 세션별 결과를 통합하고, 위험도에 따라 사람 리뷰 수준을 조절합니다.
  • 오케스트레이션: 지휘 세션은 분배·검증을, 작업 세션은 구현을 담당하며, 모든 작업에는 명확한 완료 기준과 실행 결과가 필요합니다.

결론

최신 Claude Code 사용법의 핵심은 더 많은 지시문이나 더 강한 모델을 추가하는 것이 아닙니다. 모델이 이미 코드에서 알 수 있는 내용은 덜어내고, 되돌릴 수 없는 행동은 권한과 샌드박스로 제한하며, 결과의 정확성은 테스트·훅·CI로 증명하는 구조를 만드는 것입니다. 사람이 해야 할 일은 작업 목표와 경계를 명확히 정하고, 자동화된 검증 결과와 최종 사용자 시나리오를 확인하는 데 집중해야 합니다.
